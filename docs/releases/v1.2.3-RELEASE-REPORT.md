## Phase 5 — Concurrent Activation

**Same-cluster, N=10, LIVE-PROVEN**: fired 10 concurrent first-touch HTTP
requests simultaneously against a freshly-registered, not-yet-activated
cluster. Result: **exactly 1** `activate ... generation=1 reason=ensure-active`
log line (not 10), all 10 requests succeeded, goroutines settled at a normal
single-informer-set count (311 — not a multiple suggesting duplicate informer
sets). No deadlock (verified by confirming the backend remained responsive via
`/metrics` throughout and all 10 client processes exited cleanly).

**Cross-cluster (A doesn't block B)**: **not live-tested** — the lab has only
one real cluster/API server available, and fabricating a second independent
control plane to test this live was explicitly out of scope per the brief's own
instruction ("do not fabricate independent control planes if the lab shares one
API server"). **CODE-PROVEN** via the existing
`TestEngineLifecycleManager_EnsureActive_ConcurrentDifferentClusters_NoCrossBlocking`
unit test (confirmed green in this session's regression run — see Phase 8),
which achieves genuine cross-cluster isolation using separate fake clientsets,
something only possible in a mocked environment.

N=1/5 not separately run — N=10 (the superset case) already produced clean,
unambiguous evidence; running smaller N values would not have added information.

## Phase 6 — Repeated Lifecycle / Short-Duration Stability Test

**One complete real cycle** was executed end-to-end with the genuine (not
artificially shortened) 10-minute idle TTL: register → activate → use → idle →
stop (idle_for=10m9s) → reactivate (fresh generation) → remove → re-register →
second activation. This is labeled accurately per the explicit instruction:

**"Short-duration lifecycle stability test" — ONE full cycle, LIVE-PROVEN.**

**Long/repeated soak (multiple cycles, 30-60 minutes) — explicitly UNVERIFIED.**
Each additional real cycle would require another full 10-minute TTL wait;
repeating this 3+ times would consume 30+ minutes of session time. Given this
release's "small, bounded increment" mandate, one genuine full cycle was judged
sufficient evidence for this release; a dedicated longer soak is better scoped
as its own future increment if still considered valuable (the mechanism's
scale-independence is already established architecturally — TTL/generation
logic doesn't depend on resource count — so repeated cycles are expected to be
pure repetition of what cycle 1 already proved, not expected to surface new
behavior).

## Phase 7 — Failure / Recovery

Per the explicit instruction to prefer deterministic unit/race tests over live
fault injection against the lab cluster, this phase is **CODE-PROVEN / RACE-TESTED**
via the existing suite (confirmed green in Phase 8's fresh run this session):

- Activation failure / recovery, stale-generation protection:
  `TestEngineLifecycleManager_OnClusterConnected_StopsStaleEngineWithoutEagerRestart`
- Remove during active lifecycle (race): `TestEngineLifecycleManager_EnsureActiveRacesRemoval_NeverHalfState`
- Reconnect after lifecycle state existed, no resurrection: `TestVALID04_ReconnectRacesRemove_NoResurrectionNoStaleCache`
- Concurrent reconnects, no panic: `TestVALID04_ConcurrentReconnects_NoPanic`

Live fault injection (killing the API server mid-request, etc.) against the
shared lab cluster was not attempted — it risks destabilizing the cluster for
no incremental evidence beyond what the race-tested mocked suite already proves
more rigorously (the Go race detector catches concurrency bugs that a live HTTP
test cannot).
