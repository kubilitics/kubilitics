## VALID-07 Results — Structural Proof (not latency-inferred)

Used the topology response's own `metadata.buildTimeMs` field as a structural
fingerprint: a cache hit returns the frozen `buildTimeMs` of whenever the cached
entry was originally built; a genuine rebuild computes a fresh, independently-
varying value. Sequence on `GET /clusters/{id}/topology/cluster` (default/cluster
mode):

| Request | Type | `buildTimeMs` | Interpretation |
|---|---|---|---|
| 1 | normal (cold) | 148 | fresh build |
| 2 | normal | 148 (identical) | CACHE HIT |
| 3 | `force_refresh=true` | 224 (different) | GENUINE REBUILD |
| 4 | `force_refresh=true` | 151 (different again) | GENUINE independent REBUILD |
| 5 | normal | 151 (matches request 4) | CACHE HIT of latest forced result |

Repeated in `mode=namespace&namespace=profile-c-10k`: two consecutive
`force_refresh=true` calls returned `buildTimeMs=59` then `buildTimeMs=7` —
again two distinct values, confirming independent rebuilds in namespace-scoped
mode too.

**VALID-07: PASS**, both in cluster mode and namespace mode, with structural
(not timing-based) proof. No regression.

## Performance Results

Balanced profile, `GET /topology/cluster?mode=cluster&depth=0` (2,742 resources,
5,345 edges at this depth):

| | N=1 | N=5 | N=10 |
|---|---|---|---|
| Warm cache (repeat request, same key) | 40–60ms | 98–108ms/req, 132ms wall | 60–144ms/req, 183ms wall |
| Forced rebuild (`force_refresh=true`) | 1.30s | 7.45–7.62s/req, 7.64s wall | 16.7–21.9s/req, 21.9s wall |

0 failures at every N, both scenarios. Goroutines flat (40→42, no growth across
the entire session). Heap: idle ~33MB, peaked at ~1.48GB during the N=10 forced-
rebuild burst (10 simultaneous full-graph builds held in memory concurrently —
proportional to load, not a leak), confirmed to drop back to ~33MB immediately
after load ended.

## Concurrency Results — Infrastructure Attribution

Per the explicit rule against attributing degradation to Kubilitics without a
raw-API control: ran raw `kubectl get pods -A -o json` at N=10 on the same
cluster, same time window.

| N=10 concurrent | Kubilitics (topology forced-rebuild, 2,742 resources) | Raw kubectl (full pod list, 11,716 pods) |
|---|---|---|
| Latency range | 17–22s | **78–262s** |
| Failures | 0/10 | 0/10 |

The raw API server itself was measurably slower (78–262s) than it had been
earlier in the campaign at a smaller pod count (58–67s at 10,792 pods) —
indicating the lab's shared 4-CPU control plane was under heavier capacity
pressure during this test window, likely compounded by the topology stress test
itself. Kubilitics completed its (smaller-payload, depth=0) build in a fraction
of the time the raw API server took for a full pod list, with zero failures
either way.

**Classification: INFRASTRUCTURE / API-SERVER CAPACITY**, not a Kubilitics-side
defect. Confirmed via `kubectl get --raw /healthz` returning `ok` in 234ms
immediately after the stress test — the cluster was not in a broken or degraded
steady state, just under transient load during concurrent heavy LIST calls.

N=20 was **not run** — N=10 already produced stable, conclusive evidence (per
the explicit "don't escalate just because more data is better" rule), and N=20
is not part of R2's acceptance criteria.

## Cache Results

Explicitly distinguished (never mixed, per instruction):

- **Warm cache** (repeat request, same key): 40–144ms, serves the identical
  cached object (`buildTimeMs` unchanged).
- **Forced rebuild** (`force_refresh=true`): 1.3–22s depending on concurrency,
  always produces a fresh `buildTimeMs`.
- **Cold** (first request on a never-before-seen key, e.g. a fresh
  namespace/depth combination): 148ms (balanced), 7ms (dense-ns, namespace-
  scoped builds are proportionally much cheaper), 3–11ms (profile-c-10k).

## Namespace-Dense Results

`dense-ns` (1,200 pods / 60 deployments, single namespace):

- Namespace-scoped build: 7ms server build time, 235ms total request latency.
- Cross-namespace isolation: **0 leaked nodes** — every returned resource node
  belongs to `dense-ns` (excluding the expected `Namespace`/`Node` context
  nodes, which are cluster-wide reference objects by design).
- Repeated namespace switching (`dense-ns → profile-c-10k → dense-ns →
  profile-c-10k`, 4 consecutive requests): correct, isolated results every time,
  no stale data from the previous namespace.
- Truncation guard: full-depth graph for this namespace has 1,542 nodes,
  exceeding `MaxTopologyNodes=500`; the handler correctly auto-reset to depth=0
  and **transparently disclosed this** via `truncated: true` +
  `truncateReason` in the response metadata — working as designed, not a defect.

## Relationship-Dense Results

`profile-c-10k` (200 pods / 40 deployments, every deployment maximally
connected):

- Full-depth graph: 1,239 nodes — also hit the same truncation guard (same
  disclosed behavior as `dense-ns`).
- At depth=0: 176 nodes, 240 edges — `{Deployment: 40, Service: 40, Ingress: 40,
  Node: 1, Namespace: 55}`. Zero duplicate node IDs (176 total == 176 unique).
- Relationship correctness verified: `Service→Deployment` selector edges (40,
  one per app, e.g. `selects (app=rel-000)`), `Ingress→Service` routing edges
  (40, `routes // → :80`), namespace-membership edges (120). Counts and types
  are internally consistent with the generator's known structure.
- `expand` mechanism tested on a single Deployment node: correctly surfaces its
  immediate neighbors (1 ReplicaSet, 1 HorizontalPodAutoscaler) without
  requesting a full depth increase.

**Known limitation (not a defect)**: PVC/ConfigMap/Secret relationships could
not be directly verified via a single-hop `expand` from a Deployment node in
this test pass — those resources likely connect through the Pod template rather
than appearing as a direct Deployment-level edge, and the truncation guard
prevented a full depth=2 cluster view for this namespace. No incorrect or
contaminated data was observed; this is a gap in this test pass's coverage, not
a measured product defect. Per the explicit "no blind optimization without a
measured problem" rule, this was not investigated further and is **documented,
not deferred-as-a-fix** — a future session could verify this via a differently-
scoped query if it becomes relevant.

## QPS/Burst

**MEASURED, not changed.** Current `QPS=50, Burst=100` (established in an
earlier campaign phase) was validated at 10K+ scale: the client-side rate
limiter is not the binding constraint — the raw Kubernetes API server's own
capacity is (see Concurrency Results above, where raw kubectl degraded more
than Kubilitics did at the same N). No evidence was found to justify increasing
QPS/Burst further; doing so would likely just shift more load onto an
already-constrained API server. Not changed in this release, per the explicit
"do not immediately increase QPS/Burst again" instruction.

## Known Limitations

- PVC/ConfigMap/Secret relationship verification incomplete for the
  relationship-dense namespace, due to the truncation guard + expand's
  single-hop semantics (see Relationship-Dense Results above).
- N=20 concurrency not tested (not required by R2's acceptance criteria; N=10
  already produced stable, conclusive evidence).
- The raw-kubectl infrastructure-attribution control used full pod lists
  (heaviest-payload comparison available), not an exact apples-to-apples
  payload match against topology's depth=0 build (which never fetches Pods) —
  directionally conclusive, not perfectly matched.
